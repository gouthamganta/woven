## 1. Onboarding

### 1.1 Sequential Multi-Step Flow

Onboarding is a gated sequential flow. Each step must be completed before the next is accessible. The OnboardingGate component at `/app` checks the user's current step on every app load and redirects to the correct screen.

**Steps (in order):**

| Step ID | Route | Fields |
|---|---|---|
| welcome | `/onboarding/welcome` | None — introduction only |
| basics | `/onboarding/basics` | Name, gender, pronouns, birthday, city/state |
| intent | `/onboarding/intent` | Relationship intent choice; 1-sentence reflection (encrypted at rest) |
| foundational | `/onboarding/foundational` | AI-generated questions covering 5 pillar dimensions |
| photos | `/onboarding/photos` | Profile photo upload (at least 1 required) |
| details | `/onboarding/details` | Optional fields: hobbies, etc. |
| lifestyle | `/onboarding/lifestyle` | Diet, workout, children preference, drinking, smoking, religion |
| review | `/onboarding/review` | Full profile summary, review and confirm |
| start | `/onboarding/start` | Final step; transitions to main app |

### 1.2 Foundational Questions (AI-Generated)

Foundational questions are generated by OpenAI (gpt-4.1-mini) and cover 5 pillar dimensions:
- The specific pillars are product-internal; they are never labeled or named for the user
- Answers produce a vector that seeds ECHO's compatibility scoring from day 1
- These are the only structured preference data collected at onboarding

### 1.3 Intent Reflection Encryption

The 1-sentence intent reflection is encrypted before storage. It is not shown to other users.

### 1.4 Relationship Intent Options

Users select their intent from a predefined set (serious, casual, exploring, etc.). Intent is used in compatibility scoring.

## 2. Moments — Deck Tab

### 2.1 Daily Deck

A curated set of candidate profiles shown to the user each day. Deck is generated by ECHO's scoring pipeline followed by a 12-step delivery boost pipeline.

**Cap:** 5 responses per day (totalCap = 5). Once a user has responded to 5 cards (any combination of Magical, Resonant, or Pass), the deck is exhausted until the next day.

**Card display:**
- Name
- Verification badge (✓ if isVerified = true)
- Match explanation: "What caught our eye" — headline + 2–3 bullets
- ◈ Magical button
- ◇ Resonant button
- — Pass button
- Age: **never shown on deck cards**

### 2.2 Pass Action

- Recorded silently as an implicit negative signal
- No cost, no notification to the other user, no match check
- Counts toward the 5-response daily cap

### 2.3 Magical Action (◈)

- Internal value: `MAGICAL`
- Signals a full, instinctive emotional connection
- Opens ChatNote overlay before submission
- After note is written and submitted: choice + note stored
- If mutual (both submitted positive choices + notes): Balloon created immediately
- If not mutual: status set to `RECORDED_WAITING`

### 2.4 Resonant Action (◇)

- Internal value: `LOGICAL`
- Signals an intellectual or deeply aligned connection
- Same flow as Magical: opens ChatNote overlay before submission
- Match type is PURE if both chose same type, EDGE if types differ

### 2.5 ChatNote Overlay

- Required before any Magical or Resonant submission
- Character range: 20–150 characters
- Starter phrases available:
  - "Your photo made me want to say…"
  - "I'd love to talk about…"
  - "Something tells me we'd…"
- Note is private until a mutual match exists — not shown to the other user until a Balloon is created

### 2.6 Pre-Match Status States

| Status | Meaning |
|---|---|
| RECORDED_WAITING | Viewer submitted positive choice + note; other user has not yet responded |
| WAITING_FOR_OTHER_NOTE | Other user submitted a positive choice but has not written their note yet |
| PURE_MATCH_CREATED | Match created; both chose the same type |
| EDGE_MATCH_CREATED | Match created; users chose different types |

### 2.7 Delivery Boost Pipeline

The raw ECHO score is not the final deck order. A 12-step delivery boost pipeline applies modifiers including:
- Reciprocal exposure (favoring candidates who haven't seen the viewer yet)
- Orbit gravity boost (candidates the viewer has orbited on Commons)
- Dwell signal boost
- Fatigue penalties (too many exposures to the same candidate recently)
- Unmatch history penalties

## 3. Moments — Drawn Tab

### 3.1 Drawn Entries

Shows users who submitted a positive choice (Magical or Resonant) toward the viewer in the last 7 days.

**Rules:**
- Excluded: users who are already matched with the viewer, blocked users, and users currently in the viewer's Deck
- Sorted: most recent first
- Deduplicated per user (one entry per person regardless of when they submitted)
- Expiry: 7 days from the other user's choice submission

### 3.2 Expiry Countdown

Each Drawn entry displays a countdown:
- Under 24 hours: "Xh left"
- 1 day or more: "Xd left"

When the countdown reaches zero, the entry is removed from the viewer's Drawn tab.

### 3.3 Drawn Actions

- ◈ Magical: available
- ◇ Resonant: available
- — Pass: **not available** in Drawn; expiry is the implicit pass
- **Cost: 1 spark per action** (deducted from SparkWallet on submission)
- ChatNote overlay required before submission, same as Deck

### 3.4 Drawn Match Creation

Same as Deck match creation: if both users have submitted positive choices + notes (the other user already submitted theirs; the viewer's response completes the pair), a Balloon is created immediately.

## 4. Spark Economy

### 4.1 SparkWallet

Every user has a SparkWallet.

| Parameter | Value |
|---|---|
| Daily refill | +5 sparks per day |
| Wallet maximum | 10 sparks |
| Cost per Drawn action | 1 spark |

### 4.2 Ghost Refund

When a Balloon closes with no messages exchanged, both users receive 0.5 sparks as a ghost refund. This fires on three close paths:
1. Close Gracefully
2. Trial END decision
3. Auto-close of an expired trial

Ghost refund does not fire on BLOCK.

### 4.3 No Paywalls

No feature in Woven is locked behind payment. Sparks are not purchasable. The economy is entirely behavioral.

## 5. Match Creation (Balloon)

### 5.1 Balloon

A Balloon is a match — the connection window between two users.

**BalloonState values:**
- `ACTIVE` — connection window is open
- `CLOSED` — connection window has ended

**Lifespan:** 7 days from creation (Match.ExpiresAt)

### 5.2 Match Types

| Type | Condition | EdgeOwnerId |
|---|---|---|
| PURE | Both users chose the same type (both MAGICAL or both LOGICAL) | Not set |
| EDGE | Users chose different types (one MAGICAL + one LOGICAL) | Assigned randomly |

### 5.3 On Match Creation

- Both users see each other's ChatNotes (opening notes) for the first time
- Navigation goes to the chat thread
- One ChatThread exists per match (one-to-one relationship)

## 7. Chat Thread — Trial Period

### 7.1 Trial Activation

Trial applies to matches where `IsTrial = true` on the Match entity.

Timer start mechanism:
1. When User A opens the thread: `TrialUserAOpenedAt = now`
2. When User B opens the thread: `TrialUserBOpenedAt = now`; `TrialEndsAt = now + 3 minutes`

The timer does NOT start at Balloon creation time — it starts only when the second user opens the thread.

### 7.2 Trial Window

For 3 minutes from `TrialEndsAt - 3min` to `TrialEndsAt`, the thread functions as normal — both users can message freely. A countdown timer is visible in the thread UI.

### 7.3 Trial Decisions

After `TrialEndsAt`, each user sees the decision UI:

| Decision | What Happens |
|---|---|
| CONTINUE | User wants to keep talking |
| END | User is ending the match |
| BLOCK | User is closing and blocking |

**Both CONTINUE:** match continues; `FindLoveAt = now` (Find Love unlocked immediately, skipping the 5-minute reflection window)

**Either END:** match CLOSED (UNMATCH); ghost refund fires if no messages exchanged. The ending user selects a reason:
- `no_spark`
- `wrong_timing`
- `not_my_type`

End reasons are stored as `TrialEndReason` and fed to ECHO as behavioral signals. They are never shown to either user.

**BLOCK:** match CLOSED (BLOCK reason); a Block record is created preventing future matches. No ghost refund.

## 8. Chat Thread — Find Love

### 8.1 Trigger

Find Love unlocks 5 minutes after `BothMessagedAt` (the timestamp when both users have sent at least one message in the thread).

Exception: if both users CONTINUE a trial, `FindLoveAt = now` immediately (no 5-minute wait).

### 8.2 Countdown Timer

`showBalloonTimer = true` when:
- Both users have sent at least 1 message
- 5 minutes have not yet elapsed

The countdown is visible in the thread UI.

### 8.3 Date Ideas

When Find Love unlocks (`showFindLove = true`):
- 3 date ideas appear in the thread
- Each idea: max 15 words
- Covers distinct activity types (one active, one social, one casual as a pattern)
- If shared hobbies detected: at least 1 idea incorporates them
- Personalized using viewer history: tone that preceded fast first contact, prior date idea choices

Each idea is a card with a **Plan It** button.

### 8.4 Plan It Selection

- User taps Plan It on one idea
- "Waiting to see if they're in…" shown until partner selects
- When both users have selected: push notification fires to both; venue suggestions unlock

### 8.5 Fallback Ideas

If OpenAI is unavailable at idea generation time, hardcoded fallback ideas are used per match bucket type.

### 8.6 Signal Recording

When a user selects a date idea: `DateIdeaAccepted` signal recorded with the idea text and index. This feeds ECHO's date preference learning.

## 9. Chat Thread — Games

### 9.1 Know Me

**Setup:** One user initiates, selecting a difficulty and tone.

**Difficulty levels:**

| Level | Guessability |
|---|---|
| EASY | ~80% guessable |
| MEDIUM | ~50% guessable |
| HARD | ~30% guessable |

**Tone options:** PLAYFUL, THOUGHTFUL, BALANCED

**Flow:**
1. 3 questions generated by AI from the target user's real profile data
2. The guesser predicts how the target would answer each
3. The target self-rates each dimension
4. Score = number of predictions that matched self-ratings

### 9.2 Red Flag / Green Flag

**Flow:**
1. 3 statements generated by AI about one user from their real profile data
2. Guesser rates each statement:
   - GREEN ✅ (this is true / positive)
   - YELLOW ⚠️ (uncertain)
   - RED 🚩 (red flag)
   - DEPENDS 🤷 (context-dependent)
3. Target then self-rates each statement using the same scale
4. Score = number of aligned ratings
5. 90-second time limit
6. AI generates a 1–2 sentence post-game insight about the pair

## 10. Chat Thread — Voice Notes

### 10.1 Recording

- User holds the mic button in the thread input bar to record
- Recorder: browser MediaRecorder API
- Maximum duration: 180 seconds
- On release: recording stops

### 10.2 Upload Flow

1. Frontend requests a SAS token: `POST /media/upload-token`
2. Frontend uploads audio directly to Azure Blob Storage via HTTP PUT with the SAS token
3. Frontend confirms upload: `POST /media/confirm`
4. Frontend sends voice message: `POST /chats/{threadId}/voice-message`

### 10.3 Message Storage

Voice messages stored as:
- `MessageType = "VOICE"`
- `MetaJson = { audioUrl, durationSecs }`

### 10.4 Playback

Recipient sees an audio player in the thread. The player displays duration.

### 10.5 Signal Recording

- When recipient listens to a voice note all the way to the end: `VoiceNoteListenComplete` signal recorded by ECHO
- If both users have sent at least one voice note in the same thread: `MutualVoiceExchange` signal recorded
- These are behavioral signals — they are never shown to either user

## 14. Chat Thread — Close Paths

### 14.1 Close Gracefully

- Available at any point in an active match
- User-initiated: tap "Close Gracefully" in the thread
- Match state: CLOSED
- Ghost refund: fires if no messages were exchanged in the thread

### 14.2 Trial END Decision

- User selects END at the trial decision screen
- End reason collected: no_spark / wrong_timing / not_my_type
- Match state: CLOSED (UNMATCH)
- Ghost refund: fires if no messages exchanged

### 14.3 Auto-Close (Expired Trial)

- Trial decision window elapsed with no CONTINUE from one or both users
- Match state: CLOSED
- Ghost refund: fires if no messages exchanged

### 14.4 BLOCK

- User selects BLOCK at trial decision screen or via a block action elsewhere
- Match state: CLOSED (BLOCK reason)
- Block record created, preventing future matches
- Ghost refund: does not fire

### 14.5 Balloon Expiry

- Match.ExpiresAt elapsed (7 days from match creation)
- Match state: CLOSED
- Ghost refund: depends on message state

## 15. Commons

### 15.1 Content Feed

Commons is the content layer of Woven. Users post tiles that appear in other users' feeds.

**Tile types:**
- Text
- Photo
- Video
- Voice recording

**Tile lifespan:** configurable expiry, typically 7 days.

### 15.2 Moderation Queue

All tiles enter a moderation queue before appearing in feeds. The ModerationWorker processes queued tiles.

### 15.3 Browsing

Users scroll through tiles from other users. Each tile displays the content and the poster's name/badge.

### 15.4 Energy Meter

An energy meter tracks how many tiles the user has viewed in the current day. This bounds passive browsing sessions and keeps dwell signals meaningful.

### 15.5 Orbit (◈) on Tiles

The ◈ Orbit action on a tile is an explicit romantic interest signal.

**What it does:**
- Sends a signal to the tile owner
- Generates an OrbitGravity score for the (viewer, tile owner) pair
- OrbitGravity feeds directly into ECHO's candidate pool scoring

Orbit is the highest-value signal a user can send to another user outside of the match flow.

### 15.6 My Tiles (Profile Highlights)

Users can designate up to 9 of their own tiles as profile highlights. These appear in the Highlights section of their profile. Tiles are assigned to slots 1–9.

### 15.7 Weekly Vibe

Users can set a `UserWeeklyVibe` — a short expression of where they are this week. The vibe expires weekly.

## 17. ECHO Matching Engine

ECHO is Woven's behavioral matching pipeline. It is entirely invisible to users — no scores, no rankings, no ECHO-branded surfaces. All the below is infrastructure.

### 17.1 Scoring Components

ECHO produces a per-(viewer, candidate) pair score from 16 weighted components:

| Component Category | Examples |
|---|---|
| Pillar alignment | Foundational question dimension alignment |
| Behavioral signals | Trial continuation rate, date idea acceptance, chat depth |
| Speed signals | TimeToFirstMessageMs |
| Voice signals | VoiceNoteListenComplete, MutualVoiceExchange |
| Visual preference | CLIP-based visual embedding match |
| Voice similarity | ECAPA-TDNN 192-dim voice embedding cosine similarity |
| Orbit gravity | ◈ on tiles from Commons |
| Collaborative filtering | CfScore from similar users' preferences |

### 17.2 Delivery Boost Pipeline

Raw ECHO scores are passed through a 12-step delivery boost pipeline before becoming the daily deck order. Steps include:
- Reciprocal exposure boost
- Orbit gravity boost
- Dwell signal boost
- Fatigue penalties (too-frequent exposure to same candidate)
- Unmatch history penalties

### 17.3 Weight Learning

**Batch schedule:**
- `ConnectionScoreBatchWorker`: runs nightly at 03:50 UTC — aggregates signals into composite outcome scores per (viewer, candidate) pair
- `WeightLearningBatchWorker`: runs Sunday at 04:00 UTC — runs logistic regression on outcome scores to update per-user feature weights

After enough behavioral data, no two users use the same feature weights in candidate scoring.

### 17.4 Signal Ledger

All behavioral signals are written to `MatchSignalLog` (append-only). `OccurredAt` is the timestamp field. Signal types are defined in the `MatchSignalEventTypes` constants class.

**Key signal event types:**

| EventType | What It Captures |
|---|---|
| TimeToFirstMessageMs | Speed of first message after match |
| ChatDepthMessages | Total message count in thread |
| TrialContinued | Trial CONTINUE decision |
| TrialEndedNoSpark | Trial END, reason: no_spark |
| DateIdeaAccepted | Date idea selected (text + index) |
| VoiceNoteListenComplete | Voice note listened to completion |
| MutualVoiceExchange | Both users sent voice notes in thread |
| UserFlagged | Safety flag (never mixed into compatibility scoring) |

### 17.5 CfScore (Collaborative Filtering)

CollaborativeFilteringService exists. No worker currently runs it on a schedule (as of 2026-05-26). SharedTileAffinity matching component depends on CfScore data and is pending this worker.

### 17.6 Voice Embeddings

VoiceEmbeddingService generates 192-dimensional voice embeddings using the ECAPA-TDNN model. Embeddings are computed from profile voice samples and used for voice similarity scoring between candidates.

### 17.7 Visual Preference

VisualPreferenceService learns which visual characteristics (from CLIP embeddings) the viewer responds to positively (via Magical/Resonant choices on profile photos). This preference vector is used to select the best lead photo per viewer and to score visual compatibility.

## 18. Match Explanation

### 18.1 "What Caught Our Eye"

Every Moments deck card displays a match explanation: a headline and 2–3 bullet points explaining why ECHO surfaced this candidate for this viewer.

**What it never says:**
- A raw score ("85% compatible")
- A ranking ("#2 out of your matches today")
- Community ratings or flags

**What it does say:**
- Specific, grounded observations (based on actual signals and pillar alignment)
- Written in a tone calibrated to the viewer's pillar data

### 18.2 Tone Variants

Match explanation tone is inferred from the viewer's pillar data:

| Tone | Description |
|---|---|
| PLAYFUL | Light, warm, slightly witty |
| THOUGHTFUL | Deliberate, reflective |
| CALM | Understated, low-pressure |
| BALANCED | Neutral middle ground |

### 18.3 Generation

Generated by `MatchExplanationService` using OpenAI gpt-4.1-mini per (viewer, candidate) pair.

## 19. Notifications

### 19.1 Push Notifications — Implemented

| Trigger | Recipients |
|---|---|
| Both users select a Find Love date idea | Both users |
| Availability signal sent | Partner only |

### 19.2 Push Notifications — Not Yet Implemented

As of 2026-05-26, no service worker, VAPID setup, or Web Push endpoint exists. The following notification types are designed but not functional:
- New message in thread
- New match (Balloon created)
- Trial about to expire

## 20. Moderation

### 20.1 ModerationWorker

A background worker processes tiles submitted to Commons. Tiles do not appear in feeds until moderation is complete.

### 20.2 Safety Flags

Users can flag other users. Safety flags record a `UserFlagged` signal. Flag data is platform-only — it feeds safety review processes but is never mixed into compatibility scoring or shown to any user.

## 21. Trust and Verification

### 21.1 Verification Badge

Users with `isVerified = true` display a ✓ badge on their profile card and in chat thread headers.

A catfish detection subsystem exists (`CatfishDetection` service). Detection outputs are platform-internal and never shown to users.
