# Fundraising Guide

This document is written for the founder preparing for investor conversations. Every claim here is grounded in what is actually built and running in the Woven codebase. No invented metrics, no aspirational fiction.

---

## The Technical Moat

Woven's matching engine (ECHO) is not a filter. It is a per-user adaptive model that improves as behavioral data accumulates.

The flywheel:

1. User behavior generates signals (BalloonPopped, TrialAccepted, ConversationDepth, DateAccepted, ExplicitFeedback, LoveReactions, TimeToFirstMessageMs)
2. `ConnectionScoreBatchWorker` runs nightly at 03:50 UTC and aggregates those signals into a composite outcome score per (viewer, candidate) pair, using fixed weights: BalloonPopped=0.05, TrialRequested=0.10, TrialAccepted=0.25, ConversationDepth=0.20, DateAccepted=0.15, ExplicitFeedback=0.15, LoveReactions=0.10
3. Once a user accumulates ≥10 qualifying ConnectionScores (MinConnectionScore=0.08), `WeightLearningBatchWorker` runs on Sunday at 04:00 UTC and fits a per-user logistic regression model via mini-batch gradient ascent
4. The user's personalized weights replace the defaults in `MatchScoringService`, reshaping their daily deck
5. A better deck generates more high-quality interactions, producing better training labels, closing the flywheel loop

This flywheel does not exist in swipe-based apps. Swipe right/left is a stated preference — not a behavioral signal. ECHO's 16 scoring components draw from embeddings (PillarEmbedding, ExpressionEmbedding, IntentEmbedding, StyleEmbedding, HumorEmbedding, LifestyleEmbedding, EmotionalRhythmEmbedding, AttachmentProxyEmbedding, VoiceEmbedding) that no competitor is measuring. The moat deepens with every user-week of behavioral data.

## The Product Moat

Three product mechanics generate training data that no swipe app captures:

**Trial period**: When a match's second user opens the chat thread, a 3-minute commitment window begins. The user must choose CONTINUE, END (with a reason: no_spark / wrong_timing / not_my_type), or BLOCK. TrialAccepted carries the highest weight in ConnectionScore (0.25). This is a commitment signal — the user made a deliberate decision in real time, not a passive swipe.

**Find Love**: When both users have messaged, Find Love unlocks 3 personalized date ideas generated by `MatchExplanationService` using gpt-4.1-mini, tone-adapted to the viewer's communication style. The user's selection is recorded as `DateIdeaAccepted` (weight 0.15 in ConnectionScore) — a revealed preference for an activity context, not a stated one.

**Games**: `KnowMeAgent` and `RedGreenFlagAgent` surface preference discovery and values alignment inside the chat thread. Every game round is also a behavioral signal that feeds the embedding pipeline.

Voice: A SpeechBrain ECAPA-TDNN sidecar (192-dimensional embeddings) runs self-hosted on Azure Container Apps. Voice note listening is tracked (`VoiceNoteListenComplete`) and mutual exchange is detected (`MutualVoiceExchange`). No competitor is computing vocal-rhythm compatibility.

Each of these mechanics is training data collection disguised as product experience. Users never see the model — they see a better deck.

## What to Be Honest About

Investors who dig will find these gaps. Get ahead of them.

**Push notifications**: VAPID keys are configured in infrastructure, but the service worker is not deployed. Users must be in-app to receive notifications. Fix: deploy a standard Web Push service worker. This is a known gap, not a design choice.

**CfScore batch job**: `CollaborativeFilteringService` exists in the codebase. The `CfBatchWorker` is not scheduled. This means the `SharedTileAffinity` scoring component (which depends on collaborative filtering scores) is not contributing to match scoring yet. Fix: wire the CfBatchWorker into the scheduler in `Program.cs`.

**JWT in localStorage**: dev convenience. Acceptable for a closed beta, not for general availability. Fix: move to httpOnly cookie before broad user rollout.

**WeightLearningBatchWorker eligibility**: users below 10 qualifying ConnectionScores run on default weights. In early beta, most users will be in this regime. The personalized flywheel has not kicked in yet for any user until that threshold is crossed.

Frame these honestly: the architecture is designed for these to be filled in. The gaps are in infrastructure wiring and scheduling, not in the core ML pipeline or product mechanics.

## The Right Narrative

**Behavioral AI vs. stated preferences**: Every dating app asks users what they want. Woven watches what they do. Stated preferences are unreliable; behavioral signals are not.

**Invisible UX vs. explicit AI features**: ECHO never surfaces a compatibility score to users. There is no "92% match" label. The AI's output is deck ordering — the user's experience is simply that the people they see feel more relevant over time. This is a deliberate design principle, not a limitation.

**Curated vs. infinite scroll**: The daily deck is finite. Users see a limited set of candidates per day. Scarcity creates intentionality. Intentionality creates better behavioral signals. Better signals improve the model.

**Commitment mechanics vs. passive browsing**: The Trial period forces a decision within 3 minutes of a real conversation starting. This is the highest-signal event in the ConnectionScore formula. It is what separates Woven's training data quality from any passive-swipe app.

## Infrastructure Readiness

The production infrastructure is not a demo environment:

- Terraform-managed: all Azure resources defined in `infra/main.tf`, reproducible from scratch
- OIDC CI/CD: GitHub Actions authenticate to Azure via OIDC (no long-lived secrets in CI)
- Multi-stage Dockerfiles: separate build and runtime stages for both frontend and backend
- `WOVEN_DISABLE_BATCH_WORKERS` environment variable: allows running backend in API-only mode for safe staging/testing without triggering scheduled batch jobs
- pgvector: installed on PostgreSQL Flexible Server, 9 embedding modalities stored as vector columns
- Autoscaling: Container Apps configured for horizontal scale — no manual scaling needed
- AES-256-GCM encryption on PII fields at the application layer

This is production-grade infrastructure. It is not a Heroku prototype.

## The Metrics Story

Do not lead with DAU or MAU in investor conversations. Those metrics are easy to inflate and hard to interpret in a pre-scale dating app. Lead with signal quality:

**ConnectionScore accumulation rate**: how fast are users generating meaningful behavioral events? A user accumulating ConnectionScore labels at a healthy rate is a retained user, not just a logged-in user.

**Trial continuation rate**: the fraction of trial periods ending in CONTINUE rather than END or BLOCK. This is the most direct signal of match quality — the user had a real conversation, made a deliberate choice, and chose to stay. It carries the highest weight in ConnectionScore (0.25) for this reason.

**Find Love conversion rate**: the fraction of mutual conversations that reach the `BothMessagedAt` milestone and then unlock Find Love. This measures progression through the connection funnel.

**Date idea acceptance rate**: of the 3 personalized date ideas shown at Find Love, what fraction result in a `DateIdeaAccepted` event? This measures whether the AI's tone adaptation and context reasoning are producing relevant suggestions.

**WeightLearningBatchWorker eligibility rate**: what fraction of active users have crossed the 10-ConnectionScore threshold? This is the "flywheel engaged" metric — below it, ECHO runs on defaults.

These metrics measure real connection quality, not engagement theater. Frame them that way.

## What's Next

The four highest-impact near-term completions:

1. **Push notifications**: deploy Web Push service worker. Notification surface is currently unreachable without app open.
2. **CfScore batch job**: schedule `CfBatchWorker`. Enables `SharedTileAffinity` scoring component, which adds collaborative filtering signal to match scoring.
3. **PreferenceEmbedding from ChatNotes**: wire the existing stub. Adds an additional behavioral preference signal derived from in-conversation note-taking.
4. **Premium tier design**: the spark economy (5 sparks/day free, 1 per Drawn action, 0.5 ghost refund) creates a natural monetization gate without hard paywalls. Premium tier design space exists but has not been built intentionally — validating core product first.

Each of these is an extension of infrastructure or wiring already present in the codebase, not a greenfield build.
